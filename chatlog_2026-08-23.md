## Tur 5 — 2026-08-05T16:46:42.489Z

**Bruker:**

jeg vil nå gjerne ha en SQL-spørring for å opprette disse tabelene (ja, Primary Key på (list_id, list_item_id).

**Copilot:**

Kjør disse i **rekkefølge** (viktig pga. FK-avhengighetene i `custom_list_entries`):

```sql
CREATE TABLE list_items (
    list_item_id  BINARY(16)   NOT NULL,
    title         VARCHAR(255) NOT NULL,
    imdb_id       VARCHAR(20)  NULL,
    tmdb_id       VARCHAR(20)  NULL,
    tvdb_id       VARCHAR(20)  NULL,
    cover_image   VARCHAR(255) NULL,
    PRIMARY KEY (list_item_id)
);

CREATE TABLE custom_lists (
    list_id       BINARY(16)   NOT NULL,
    list_name     VARCHAR(255) NOT NULL,
    PRIMARY KEY (list_id),
    UNIQUE KEY uk_list_name (list_name)
);

CREATE TABLE custom_list_entries (
    list_id        BINARY(16) NOT NULL,
    list_item_id   BINARY(16) NOT NULL,
    PRIMARY KEY (list_id, list_item_id),
    CONSTRAINT fk_entries_list      FOREIGN KEY (list_id)      REFERENCES custom_lists(list_id),
    CONSTRAINT fk_entries_list_item FOREIGN KEY (list_item_id) REFERENCES list_items(list_item_id)
);
```

`list_items` og `custom_lists` må opprettes før `custom_list_entries`, siden dens FK-er peker på dem.

## Tur 6 — 2026-08-05T16:49:19.027Z

**Bruker:**

hmm... hvordan opprette post hvis det er binary(16) ? Altså i f.eks. phpmyadmin?

**Copilot:**

**Viktig rettelse** i siste eksempel — siden `list_id` allerede er lagret som binær, skal ikke subquery-resultatet pakkes i `UUID_TO_BIN()` igjen:

```sql
INSERT INTO custom_list_entries (list_id, list_item_id)
VALUES (
    (SELECT list_id FROM custom_lists WHERE list_name = 'Julefilmer'),
    UUID_TO_BIN('a1b2c3d4-e5f6-7890-abcd-ef1234567890')
);
```

**For å lese ut verdiene** senere (f.eks. i en SELECT), bruk `BIN_TO_UUID()`:
```sql
SELECT BIN_TO_UUID(list_id) AS list_id, list_name FROM custom_lists;
```

**Oppsummert i phpMyAdmin:**
1. Gå til **SQL**-fanen (ikke Insert-skjemaet) for tabellen/databasen.
2. Lim inn en `INSERT`-spørring som over, med `UUID_TO_BIN(UUID())` for å auto-generere ny ID, eller `UUID_TO_BIN('din-uuid-streng')` for en spesifikk verdi.
3. For å se data lesbart, bruk `BIN_TO_UUID(kolonnenavn)` i SELECT-spørringer — rå Insert-skjemaet vil vise ubrukelig gibberish for `binary(16)`-felt.

Dette er nøyaktig samme mønster koden i `physical_collection_import.py` bruker internt (Python genererer `uuid.uuid4().bytes` og sender rått til MySQL) — `UUID_TO_BIN()`/`BIN_TO_UUID()` er MySQL-ekvivalenten når du jobber manuelt via phpMyAdmin.

## Tur 38 — 2026-08-21T18:59:42.874Z

**Bruker:**

Kan du foreslå (men uten å gjøre endringer) - et forslag til struktur i databasen, for behandling av data når det kommer til filmer jeg har digitalt (hovedsaklig på Plex Media Server)? Se forøvrig ER_diagram.png for nåværende struktur - tabellen 'content' skal brukes.

**Copilot:**

Har sett gjennom `ER_diagram.png`. Her er et forslag til utvidelse for digitalt innhold (Plex), bygget på samme mønster som de fysiske tabellene (`physical_collection` → `content_in_physical_collection` → `disc`/`disc_in` osv.), og med `content` som felles rot slik du ønsker. **Ingen endringer er gjort — dette er kun et forslag.**

## Foreslåtte nye tabeller

**1. `digital_library`** — ett Plex-bibliotek/seksjon (i tilfelle flere servere/seksjoner)
```
library_id      binary(16)  PK
server_name     varchar(100)      -- f.eks. "plexcity-main"
section_key     varchar(20)       -- Plex sin interne seksjons-ID
section_name    varchar(100)      -- f.eks. "Movies"
library_type    varchar(20)       -- 'movie' | 'show'
created_at      timestamp
```

**2. `content_in_digital_library`** — kobler `content` til biblioteket (analogt med `content_in_physical_collection`)
```
library_id        binary(16)  FK, PK
content_id        binary(16)  FK, PK
plex_rating_key   varchar(20)       -- Plex sin unike ID for elementet
added_at          timestamp         -- når Plex la den til
last_synced_at    timestamp
available_flag    tinyint(1)        -- for historikk hvis filen fjernes fra Plex
PK (library_id, content_id)
UK (plex_rating_key)
```

**3. `digital_media_version`** — én rad per faktisk "Media"-objekt i Plex (kvalitet/versjon), analogt med `disc`
```
version_id       binary(16)  PK
content_id       binary(16)  FK
edition_title    text              -- f.eks. "Director's Cut"
resolution       varchar(10)       -- "1080p", "4K"
video_codec      varchar(20)
audio_codec      varchar(20)
container        varchar(10)       -- mkv, mp4 osv.
bitrate          int(11)
duration_ms      int(11)
quality_profile  varchar(50)       -- fritekst-oppsummering, f.eks. "2160p HEVC HDR"
created_at       timestamp
```

**4. `digital_media_part`** — enkeltfiler tilhørende en versjon (Plex "Part"-objekt, for filer delt i flere deler), analogt med `disc_bonus_item`
```
part_id          binary(16)  PK
version_id       binary(16)  FK
part_index       int(11)
file_path        text
file_size_bytes  bigint
duration_ms      int(11)
PK (version_id, part_index)
```

**5. (Valgfritt) `digital_storage`** — kun relevant hvis filene ligger spredt på flere disker/NAS-volum, analogt med `storage`/`disc_in_storage`
```
storage_id     binary(16)  PK
storage_name   varchar(100)   -- f.eks. "NAS-Volum1"
mount_path     text
capacity_gb    int
```
og en kobling `digital_part_in_storage(storage_id, part_id)` hvis en fil kan flyttes mellom volum over tid.

## Gjenbruk av eksisterende tabell

`content_external_source` (som allerede finnes) kan brukes med `source = 'plex'` for å lagre rå Plex-metadata (GUID, thumb, art, summary, `data_json`) — akkurat slik den allerede fungerer for TMDB/IMDb/TVDB. Da slipper du å duplisere API-respons-lagring; kun operasjonelle/spørrbare felter (filsti, oppløsning, størrelse) går i de nye relasjonstabellene.

## Begrunnelse for strukturen

- Speiler samme mønster som fysisk-delen: `content` er fortsatt sannhetskilden for tittel/år/cover, mens en junction-tabell (`content_in_digital_library`) håndterer "finnes dette digitalt et sted".
- `digital_media_version`/`digital_media_part` håndterer at Plex kan ha flere versjoner (kvalitet, cut) og flere filer per versjon — akkurat som `disc`/`disc_bonus_item` håndterer flere plater/bonusmateriale.
- `binary(16)` som PK-type er konsistent med resten av databasen.
- `available_flag` og `last_synced_at` gir mulighet til å beholde historikk selv om Plex-biblioteket endres (f.eks. hvis en fil slettes, men du vil beholde info om at den *har* vært tilgjengelig digitalt).

Si ifra om du vil justere noe (f.eks. droppe `digital_storage` hvis du kun har én disk, eller slå sammen version/part hvis du sjelden har flerdelte filer) før jeg eventuelt lager CREATE TABLE-spørringer.

**Copilot:**

Her er et skisse-forslag for hvordan `locked_fields` / `is_manually_edited` kan fungere — fortsatt kun et designforslag, ingen endringer gjort i databasen.

## To varianter å velge mellom

**Variant A — grovkornet (hele raden låst)**
```
ALTER TABLE content ADD COLUMN is_manually_edited tinyint(1) NOT NULL DEFAULT 0;
```
Enkel logikk: hvis `is_manually_edited = 1`, rører import-scriptet **ingen** felter i denne `content`-raden i det hele tatt (kun nye `digital_media_version`/`digital_media_part`-rader oppdateres). Enkelt å forstå, men alt-eller-ingenting — hvis du bare har rettet tittelen, mister du likevel automatisk oppdatering av f.eks. `runtime` eller `cover_image` fra Plex.

**Variant B — finkornet (kun spesifikke felter låst)** — *anbefalt, siden du nevnte "tittel på et annet språk" som eksempel, ikke hele raden*
```
ALTER TABLE content ADD COLUMN locked_fields varchar(255) NULL;
-- Kommaseparert liste over kolonnenavn, f.eks: "title,cover_image"
```
Import-scriptet sjekker per felt om det står i `locked_fields` før det oppdaterer:

```python
locked = set((row.locked_fields or "").split(","))

updates = {}
if "title" not in locked:
    updates["title"] = plex_title
if "cover_image" not in locked:
    updates["cover_image"] = plex_cover_url
if "runtime" not in locked:
    updates["runtime"] = plex_runtime
# ... osv per felt

if updates:
    db.execute(update(content).where(content_id=...).values(**updates))
```

Når du selv redigerer et felt manuelt via et fremtidig admin-skjema, legger skjemaet automatisk til feltnavnet i `locked_fields` (hvis det ikke allerede er der).

## Alternativ normalisert modell (hvis du foretrekker rene relasjoner fremfor kommaseparert tekst)

```
content_field_lock
  content_id    binary(16)  FK, PK
  field_name    varchar(50) PK
  locked_at     timestamp
PK (content_id, field_name)
```
Mer "riktig" relasjonelt, lett å spørre ("vis alle låste felter for film X"), men krever en ekstra JOIN i importlogikken sammenlignet med en enkel tekstkolonne.

## Min anbefaling

Start med **Variant B med kommaseparert `locked_fields`-kolonne** — det er enkelt å implementere, lett å lese/debugge (`SELECT locked_fields FROM content WHERE ...`), og dekker behovet ditt (låse enkeltfelt som tittel) uten unødig kompleksitet. Du kan alltid migrere til den normaliserte modellen senere hvis behovet vokser (f.eks. hvis du vil vite *når* et felt ble låst).
